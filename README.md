# DevLog

DevLog — трекер задач для невеликої інженерної команди з вбудованими AI-агентами. Можна створювати, фільтрувати й сортувати задачі, вести підзадачі й нотатки. Нову задачу можна [продиктувати українською](#голосове-створення-задачі). Чотири агенти допомагають вибрати пріоритети на день, розбити задачу, написати статус-апдейт і знайти застряглі задачі. Зміни задач потребують підтвердження користувача, а чернетки можна скопіювати для ручного надсилання.

Локально DevLog працює з SQLite. Застосунок запускається без ключів у деморежимі. Для live-режиму потрібен серверний ключ OpenAI.

## Швидкий старт

Потрібен Node.js LTS (`>=22 <25`). У `.nvmrc` закріплено Node.js 22.

```bash
npm install
npm run dev
```

Відкрийте <http://localhost:3000>. База SQLite створюється автоматично (`./data/devlog.db`). Файл `.env` не потрібен: без `OPENAI_API_KEY` застосунок стартує в **demo-режимі** (угорі сторінки банер «Демо-режим AI»), де агенти відповідають детермінованими моками.

Щоб завантажити 12 демозадач із підзадачами й нотатками, виконайте команду в чистому клоні або з окремим `DATABASE_URL`. Вона замінює наявні задачі та видаляє історію запусків агентів у вибраній базі.

```bash
npm run db:seed
```

### Запустити через Docker

Потрібен Docker із Compose. Запустіть Compose у корені репозиторію.

```bash
docker compose up --build
```

Відкрийте <http://localhost:3000>. Контейнер запускається в деморежимі й доступний лише з цієї машини. Задачі, нотатки й історія агентів зберігаються в іменованому томі `devlog-data` після зупинки чи заміни контейнера.

За потреби завантажте демонстраційні задачі в порожній том. Команда замінює поточні задачі й історію агентів у цьому томі.

```bash
docker compose stop app
docker compose run --rm --build seed
docker compose up -d
```

Зупинити застосунок і зберегти том можна командою `docker compose down`.

### Увімкнути live-режим

```bash
cp .env.example .env     # і заповніть лише потрібне
# OPENAI_API_KEY=...     # ключ живе тільки на сервері, у браузер і логи не потрапляє
# OPENAI_MODEL=...       # за замовчуванням gpt-4.1-mini
```

Запустіть локальний сервер командою `npm run dev -- --hostname 127.0.0.1`. Без явного `AI_MODE` ключ вмикає `live`, а порожній ключ залишає `demo`. Режим `AI_MODE=live` потребує ключа. У `live` OpenAI отримує промпт і дані задач, які агент читає через tools.

## Публічне демо на Vercel

Production-адреса після публікації — [devlog-zeta-fawn.vercel.app](https://devlog-zeta-fawn.vercel.app).

Демо має окрему SQLite-сумісну базу Turso зі спільними демонстраційними задачами. Відвідувачі можуть бачити й редагувати той самий набір задач. Локальні файли SQLite та дані інших середовищ зберігаються окремо.

У Vercel Production діє **спільний ліміт 150 запусків AI** на всіх відвідувачів. Його використовують план на день, радар застряглих, голосове створення задач, декомпозиція й статус-апдейти. У меню **«Спроби AI»** видно загальний залишок і кількість використаних спроб за кожною функцією. Сервер резервує спробу перед викликом моделі. Повторний запуск декомпозиції після уточнення також витрачає спробу. Наявні лічильники входять до загального ліміту, який зберігається між деплоями й не скидається автоматично. Ручне додавання підзадач і збереження вже запропонованих підзадач доступні навіть після вичерпання квоти. Голосовий запис автоматично зупиняється через 60 секунд. Один запуск може містити кілька викликів моделі з окремими лімітами кроків і токенів.

Для релізу підключіть до Production окрему базу Turso та серверний `OPENAI_API_KEY`. Інтеграція Turso надає `TURSO_DATABASE_URL` і `TURSO_AUTH_TOKEN`. Для ручного налаштування використовуйте пару `DATABASE_URL` і `DATABASE_AUTH_TOKEN`. У налаштуваннях Vercel увімкніть системні змінні середовища, щоб застосунок отримав `VERCEL_ENV`. Preview використовує іншу базу й деморежим. [Налаштування Turso на Vercel](https://vercel.com/marketplace/tursocloud/database)

Перед першим деплоєм прив’яжіть каталог до Vercel-проєкту командою `vercel link`. Передайте командам саме змінні Production. Якщо хоча б однієї змінної Turso бракує, команда зупиниться.

```bash
vercel env run -e production -- sh -ec '
  test -n "$TURSO_DATABASE_URL" && test -n "$TURSO_AUTH_TOKEN" || exit 1
  export DATABASE_URL="$TURSO_DATABASE_URL" DATABASE_AUTH_TOKEN="$TURSO_AUTH_TOKEN" AI_MODE=demo
  npm run db:migrate
  npm run db:seed:remote
'
```

Під час наступних релізів застосовуйте нові міграції через `db:migrate`. Засівання віддаленої бази завантажує демонстраційні задачі в порожню базу. Повторний запуск зберігає наявні задачі й лічильники.

## Архітектура

Стек: Next.js (App Router) + TypeScript `strict`, Route Handlers як REST API, SQLite і Turso через libSQL + Drizzle ORM, Zod, Tailwind CSS + shadcn/ui, TanStack Query, `openai` SDK, `pino`, Vitest + Playwright.

Клієнт організований за **Feature-Sliced Design**, сервер — за **DDD**:

```
src/
  app/        Next.js routing: тонкі page / layout / route.ts (parse → service → response)
  views/      сторінки (список, деталі задачі)
  widgets/    великі блоки екрана: панелі агентів, список нотаток
  features/   дії користувача: створення, фільтри, декомпозиція, статус-апдейт, радар
  entities/   сутності: task, agentRun — ui + model (Zod-схеми й типи)
  shared/     ui (shadcn), lib, config, api
  server/     tasks/ (domain, repository, service), db/, agents/ (core + по агенту), logger
```

Імпорти йдуть лише вниз (`app → views → widgets → features → entities → shared`), назовні slice віддає тільки `index.ts`; це перевіряє ESLint. API, форми й tools агентів використовують спільні Zod-схеми. Репозиторії `server/tasks/repository.ts` і `server/agentRuns/repository.ts` зберігають в SQLite задачі та історію запусків відповідно.

**Потік запиту:**

```
UI → TanStack Query → route handler (Zod) → service → repository → SQLite
```

**Потік агента:**

```
UI → POST /api/agents/<kind> → runAgent ↔ модель / tools → валідація → NDJSON-події → useAgentRun → UI
```

Помилки API мають єдиний формат `{ error: { code, message, details? } }`. Дизайн-система, токени й карта компонентів — у [`docs/design/DESIGN.md`](docs/design/DESIGN.md).

## AI-агенти

Усі чотири агенти працюють на спільному ядрі `src/server/agents/core/runAgent.ts` — це власний цикл, а не один запит до моделі:

1. модель отримує системний промпт, повідомлення користувача й список tools;
2. якщо вона просить tool — ядро валідує вхід Zod-схемою, виконує tool (лише читання) і повертає результат (або `is_error`); цикл повторюється;
3. модель завершує роботу викликом спеціального tool `submit_result` зі strict-схемою;
4. результат проходить Zod-валідацію і **перевірку фактів** (`factCheck`); при порушенні модель отримує список порушень і **один раз** повторює спробу; якщо знову невдало — **детермінований fallback** без AI, який проходить ті самі перевірки;
5. кожен крок пишеться в `agent_steps`, кожен запуск — в `agent_runs` (trace для UI і дебагу), клієнт отримує події потоком NDJSON.

**Спільні межі.** Максимум викликів моделі за запуск — `AGENT_MAX_STEPS` (за замовчуванням 8); до 5 викликів tools за хід; вивід tool обмежений 32 КіБ; загальний дедлайн запуску 120 с. Відмова моделі (`refusal`), обрізана відповідь (`max_tokens`), вичерпаний ліміт кроків, відсутній `submit_result` і перевищений дедлайн завершують запуск fallback-ом із причиною. Кнопка «Зупинити» перериває запит (статус `stopped`), дані не змінюються. Усі tools — лише читання: агенти не мають доступу до запису в БД.

### A. План на день

- **Навіщо.** Відповідає на «з чого почати?»: пропонує top-3 задач на сьогодні з поясненням, чому саме вони, і що свідомо відкладено.
- **Кроки й tools.** `list_active_tasks` (активні задачі з віком, днями без змін, дедлайном, температурою й вагою), за потреби `get_task`. Кроки в UI: зібрати активні задачі → зважити пріоритет, вік, статус і дедлайни → скласти порядок і пояснення → перевірити відповідь.
- **Як вирішує, що далі.** Модель сама обирає, чи читати деталі окремих задач; детермінована підказка — вага задачі (`score`) і прапорець `urgent` (дедлайн менш ніж за 48 год) у виводі `list_active_tasks`.
- **Коли зупиняється.** Після `submit_result`, що пройшов перевірку; інакше — повтор, fallback, ліміт кроків, `refusal` / `max_tokens`, «Зупинити».
- **Structured output — `DayPlan`.** `items[]` (1–3 задачі з `taskId`, `why` на 20–300 символів і `joke` до 200 символів або `null`) і `deferred[]` (до 3 задач з `taskId` і `reason` до 200 символів).
- **Валідація.** Zod + `checkDayPlan` перевіряє, що кожен `taskId` існує, задача не `done`, повторів немає, а `why` називає реальний фактор (пріоритет, вік, дні без змін, статус або дедлайн). Термінові задачі мають пріоритет над рештою й займають до трьох місць у плані. Fallback ставить термінові задачі першими й сортує решту за пріоритетом, віком і статусом.
- **Підтвердження.** План — лише пропозиція. Позначка «Фокус #N» з'являється після «Застосувати порядок» і підтвердження в діалозі (`PUT /api/tasks/focus`); статуси й пріоритети агент не змінює.

### B. Декомпозиція

- **Навіщо.** Розбиває задачу на 3–6 підзадач з оцінкою часу й поясненням; якщо задача розмита, спершу ставить уточнювальні питання.
- **Кроки й tools.** `get_task` (назва, опис, наявні підзадачі й нотатки), `assess_clarity` (чи достатньо чіткий опис — правило `isVague`). Кроки: прочитати задачу → оцінити чіткість → згенерувати підзадачі → перевірити.
- **Як вирішує, що далі.** Якщо задача розмита, модель може повернути `clarify` замість підзадач; користувач відповідає, відповідь зберігається нотаткою **до** нового запуску, тож агент читає її через `get_task`. `assess_clarity` лише підказує; рішення за моделлю.
- **Коли зупиняється.** `submit_result` з `kind: "subtasks"` (після уточнення `clarify` вже заборонений) або `kind: "clarify"` (кроки генерації й перевірки лишаються `pending`); решта — як у спільних межах.
- **Structured output — `Decomposition`.** Плоска форма, сумісна зі strict-режимом OpenAI: `kind` (`clarify` | `subtasks`), `questions[]` (1–3 для `clarify`), `items[]` (3–6 для `subtasks`: `title`, `estimate`, `rationale`); `superRefine` зводить її до union.
- **Валідація.** Zod + `checkDecomposition`: задача існує; пункти не дублюють наявні підзадачі й одне одного (нормалізоване порівняння, збіг перших символів або вкладення); `clarify` після наданого уточнення — порушення. Fallback — шаблонний набір (3–4 пункти), відфільтрований від дублікатів.
- **Підтвердження.** Підзадачі створюються лише після «Створити N підзадач» і лише ті, що обрав користувач (`POST /api/tasks/:id/subtasks`); без підтвердження нічого не змінюється.

### C. Статус-апдейт

- **Навіщо.** Складає короткий Slack-апдейт зі стану задачі, підзадач і нотаток; сам підбирає тон або бере тон, обраний користувачем.
- **Кроки й tools.** `get_task_context` (задача, підзадачі з id, нотатки, температура, дні без змін), `suggest_tone` (авто-тон). Кроки: зібрати задачу, підзадачі й нотатки → визначити контекст і тон → написати чернетку → перевірити факти.
- **Як вирішує, що далі.** Тон `auto`: закрита задача → «для команди»; гаряча або з дедлайном → «для менеджера»; інакше «для команди». Ручні тони: команда, менеджер, коротко, з гумором (у серйозному режимі гумору немає).
- **Коли зупиняється.** Після `submit_result`, що пройшов перевірку; інакше — повтор, fallback, ліміти.
- **Structured output — `StatusUpdate`.** `tone`, `text` (20–800 символів, Slack-розмітка `*жирний*`), `mentions` (`subtaskIds`, `noteIds`), `thin` (немає ні підзадач, ні нотаток).
- **Валідація.** Zod + `checkStatusUpdate`: `mentions` лише з цієї задачі; кожне посилання (`PR #n`, `#n`, URL) є в назві, описі, підзадачах чи нотатках; тон збігається із заданим (тон `short` приймається завжди — це тон fallback); для менеджера без емодзі, окрім тих, що вже є в даних задачі; `short` ≤ 200 символів; без масових згадок Slack (`@channel`, `@here`); `thin` відповідає даним. Fallback — короткий шаблонний апдейт.
- **Підтвердження.** Агент нічого не надсилає: результат лише копіюється кнопкою «Скопіювати». Прев'ю рендериться як React-текст (без `dangerouslySetInnerHTML`), тож HTML у нотатці лишається текстом.

### D. Радар застряглих

- **Навіщо.** Знаходить задачі «в роботі», що давно не рухаються, називає ймовірну причину і пропонує одну конкретну дію (докладніше — в окремому абзаці нижче).
- **Кроки й tools.** `find_stale_tasks` (in-progress без змін ≥ 3 діб, крім відкладених користувачем), `get_task_context`, `diagnose_hint` (правило-підказка). Кроки: знайти задачі → зіставити з нотатками й підзадачами → визначити причину → запропонувати дію.
- **Як вирішує, що далі.** Правило діагнозу (порядок важливий): у нотатках PR/ревʼю → «Чекає на ревʼю»; немає ні підзадач, ні нотаток → «Задача розмита»; ≥ 3 відкритих підзадач → «Задача завелика»; інакше «Немає активності». Модель підтверджує або уточнює пояснення й пише чернетки.
- **Коли зупиняється.** Після `submit_result`, що пройшов перевірку. Якщо пошук не знайшов застряглих задач, модель отримує інструкцію одразу повернути `items: []`. Demo робить це детерміновано. Порожній результат показується як «Нічого не застрягло». Діють спільні межі зупинки.
- **Structured output — `Triage`.** `items[]`: `taskId`, `cause` (`waiting-review` | `vague` | `too-big` | `no-activity`), `why`, `action` (`draft-review` | `split` | `draft-help` | `open`), `draft` (20–500 символів для `draft-*`, інакше `null`).
- **Валідація.** Zod + `checkTriage`: `taskId` серед знайдених застряглих (без відкладених) і без повторів; дія відповідає причині; чернетка лише для `draft-*`; у чернетці ревʼю згадано PR; PR-номери лише з назви й нотаток; без масових згадок Slack. Fallback — ті самі задачі, усі з дією «Відкрити задачу», без порад і чернеток.
- **Підтвердження.** Чернетки лише показуються й копіюються («Агент нічого не надсилає сам»); «Розбити на підзадачі» відкриває агента B з автозапуском, де підзадачі створюються лише після «Створити»; «Ігнорувати» ховає задачу до перезавантаження.

## Голосове створення задачі

1. У діалозі «Нова задача» натисніть **«Продиктувати задачу»** й дозвольте браузеру доступ до мікрофона.
2. Скажіть українською, що потрібно зробити. За потреби назвіть пріоритет і дедлайн. Наприклад, «Виправити зникнення аватара після оновлення профілю. Це терміново. Зробити до завтра, до 17:00».
3. Натисніть **«Зупинити запис»**. Запис також завершується автоматично через 60 секунд. У live-режимі сервер передає аудіо OpenAI для розшифровки й підготовки чернетки.
4. Перевірте й за потреби відредагуйте назву, опис, пріоритет і дедлайн. Задача зберігається після натискання **«Створити»**.

«Терміново» дає високий пріоритет, «може зачекати» — низький. За замовчуванням пріоритет середній. Відносні дати, як-от «завтра», визначаються за локальною датою. Якщо названо лише день, чернетка пропонує 23:59.

У деморежимі натисніть **«Спробувати приклад»**. Форма заповниться демонстраційною чернеткою без мікрофона й викликів OpenAI. Якщо запис недоступний або чернетку не вдалося підготувати, форму можна заповнити вручну.

## Хибні кейси і як продукт їх обробляє

Модель може повернути відповідь, яка проходить за формою (Zod), але хибна за змістом. Ми не довіряємо output: перевірка фактів ловить такі відповіді, ядро один раз просить виправитись, а якщо повтор теж хибний — показує детермінований fallback і чесне повідомлення.

| Агент | Що повернула модель | Що зловила перевірка | Що бачить користувач |
|---|---|---|---|
| **A. План на день** | План із задачею `#42`, якої не існує | `taskId 42: задачі не існує` (`checkDayPlan`) | Повтор → знову хибно → alert «Відповідь агента відхилено», крок «Перевірити відповідь» з помилкою, порядок за правилом без пояснень AI. Нічого не закріплюється без підтвердження. |
| **B. Декомпозиція** | Три пункти, що повторюють наявну підзадачу (і одне одного) | `items[i]: «…» дублює наявну підзадачу` / `повторює попередній пункт` (`checkDecomposition`) | Alert «Відповідь агента відхилено», шаблонний набір унікальних пунктів (зазвичай 4); «Створити N підзадач» працює як зазвичай. |
| **C. Статус-апдейт** | Апдейт зі згадкою `PR #999` | `У тексті згадано PR #999, якого немає в нотатках` (`checkStatusUpdate`) | Alert «Чернетку агента відхилено», крок перевірки з помилкою, короткий шаблонний апдейт; «Скопіювати» працює. |

**Як відтворити** (dev-режим, без ключа й без витрат):

1. Використайте демобазу зі швидкого старту, запустіть `AI_MODE=demo npm run dev` і відкрийте <http://localhost:3000>.
2. На сторінці списку відкрийте «Стани прототипу» іконкою в шапці, увімкніть «Зламати відповідь агента» і закрийте панель клавішею Escape.
3. Прапорець живе в пам'яті до перезавантаження сторінки. Для A і D залишайтесь на списку, для B і C відкривайте задачу кліком зі списку.
4. Для A натисніть «Скласти план на день». Для B відкрийте задачу з підзадачами (наприклад, «Виправити витік пам'яті…») і натисніть «Розбити на підзадачі». Для C відкрийте задачу й натисніть «Згенерувати апдейт». На вузькому екрані панелі B і C відкриваються вкладками «Підзадачі» й «Апдейт» відповідно. Для D натисніть «Просканувати». Після відхилення відповіді кожна картка радара пропонує відкрити задачу.

Ці сценарії покривають unit-тести (`forceInvalidOutput` → перша невдала спроба → один невдалий повтор → fallback) у `src/server/agents/*/*.test.ts` і E2E в `e2e/`.

## Live і mock

- **Що перевірено на реальному API.** Лише платний dev-smoke (`npm run smoke:ai`, до 4 викликів × 400 токенів): він перевіряє, що цикл `runAgent` працює з OpenAI Chat Completions, strict-tools і `submit_result`. Схеми `DayPlan`, `Decomposition`, `StatusUpdate` і `Triage` на live OpenAI **не перевірені**: їх лише неявно проганяє локальна перевірка strict-сумісності (`assertStrictCompatible`, наближення правил OpenAI) під час demo-запусків у тестах агентів, а не реальний виклик API. Перед живим використанням їх варто перевірити вручну (з обмеженням вартості).
- **Як працює demo.** Demo використовує `ScriptedClient`, який віддає заздалегідь підготовлений сценарій (виклики tools → `submit_result`) через **той самий** цикл `runAgent`: ті самі кроки, ті самі tools, та сама валідація, fallback і trace. Відмінність одна: відповіді детерміновані й будуються з даних задач правилами (а не моделлю), тож тексти шаблонні, а жарти й тони — з фіксованого набору. Кожен агент має mock.
- **Режим видно в UI:** банер «Демо-режим AI» угорі й позначка «мок-відповідь» у підсумку запуску.

## Агент D — навіщо

Застряглі задачі найдорожчі, бо їх ніхто не бачить, поки не стало пізно. Агент A каже, що робити сьогодні, але не каже, чому щось стоїть тиждень. D дивиться на історію (дні без змін, нотатки, підзадачі), називає ймовірну причину (чекає ревʼю, розмита, завелика) і знімає найнеприємнішу частину — написати колезі «глянь, будь ласка» або зрозуміти, з чого почати. Це власна агентна функція понад вимоги: вона закриває проблему, яку три інші агенти не бачать.

## Як ми розробляли DevLog

1. **Дослідження й план.** Уточнюємо вимоги, записуємо критерії приймання й оцінюємо ризик. Від ризику залежать ролі й глибина перевірок. Плани середніх і складних задач погоджує авторка.
2. **Реалізація й перевірка.** Розробник додає код і тести. `factory verify` перевіряє типи, ESLint, тести й наявність тесту для кожного критерію.
3. **Рев’ю й QA.** Незалежне рев’ю перевіряє код разом із тестами. За ризиком додаємо перевірку безпеки та друге рев’ю. Для UI-задач QA перевіряє поведінку в браузері. Якщо є блокувальні знахідки, задача повертається на виправлення. Оновлений код проходить перевірки й рев’ю для нового хеша.
4. **Фінальне погодження й PR.** Авторка погоджує перевірену версію, після чого створюємо PR у `stage`. Git hooks перевіряють контрольні етапи перед комітом і пушем, а GitHub Actions окремо запускає тести. Авторка приймає рішення про merge. Після завершення фіксуємо рішення, помилки й висновки в документації та ретро.

На базовій версії `stage` selftest Factory пройшов 162 перевірки. У DEV-013 невдалий `verify` і блокувальне рев’ю призвели до циклу виправлень перед PR. Надійність цього процесу залежить від сценаріїв, які покрили тести, і від знахідок рев’ю. [Архітектура Factory](docs/vault/architecture/factory.md), [запуск із чистого клону DEV-013](.factory/evidence/DEV-013/d962dc8cc989f45f81e056d02dc8af96785952bd/clean-clone.md)

Для невеликого DevLog відклали два окремі етапи. У більшому репозиторії **агент для прибирання** міг би знаходити застарілі файли, тимчасові артефакти й зайві залежності. **Аналізатор помилок з автовиправленням** міг би групувати повторювані збої, шукати причини й готувати виправлення для рев’ю. Зараз Factory розпізнає повторні провали перевірок, а виправлення робить розробник.

## Що свідомо не робимо

- Вхід до акаунта, ролі та права доступу не входили до ТЗ. Через обмежений час їх і багатокористувацький режим відклали. У публічному демо відвідувачі працюють зі спільними демонстраційними задачами.
- Для початкового MVP через обмежений час залишили локальну SQLite. Це дозволило запускати чистий клон без окремого сервера бази даних.
- drag-and-drop;
- реальну відправку в Slack: апдейти й чернетки лише копіюються;
- ручне додавання підзадач: вони з'являються лише через агента B (так підтвердження лишається єдиним шляхом створення);
- перемикач «Серйозного режиму» в production: серйозний варіант текстів є, але вмикається лише в dev-панелі.

**Відомі обмеження.** Кроки агентів у UI не показують розгорнутого `detail` (напр. «Тон: для менеджера»); посилання в чернетках агентів C і D перевіряються з різною повнотою (C суворіше); схеми агентів не перевірені на live OpenAI (див. вище).
