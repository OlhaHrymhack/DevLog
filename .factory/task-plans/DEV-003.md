# DEV-003 — Шар даних і seed

## Мета
Персистентне сховище SQLite, до якого є лише один шлях доступу: repository. Окрім нього — Zod-контракти сутностей (одні для API, форм і tools агентів), авто-міграції на старті та `db:seed` з 12 задачами прототипу. Демо-дані покривають усі рівні температури й сценарії агентів. Розблоковує DEV-004 (HTTP) і DEV-008 (агенти).

## Acceptance criteria (зі специфікації, нумерація збережена)
- AC-1: Перший запуск створює файл БД і схему (порожня тека → `getDb()` → таблиці існують; повторний виклик не падає).
- AC-2: CRUD задачі через repository зберігається між з'єднаннями (create → закрити → відкрити → `getTask` повертає ту саму задачу, TC-17).
- AC-3: Zod-схеми відхиляють невалідне: title `"  ab "`, description з 4 символів, status `"blocked"`, update з `createdAt` (strict), update `{}`.
- AC-4: Правила `updatedAt`/`createdAt`:
  - зміна статусу, додавання нотатки, перемикання підзадачі → `updatedAt = now`;
  - `setFocus` → `updatedAt` без змін;
  - `createdAt` не змінюється після всіх операцій.
- AC-5: Сортування і фільтр у repository:
  - priority desc: high → medium → low, при рівності новіші вище; asc — навпаки за пріоритетом;
  - date desc/asc — за `createdAt`;
  - `status=in-progress` повертає лише такі задачі;
  - `q="пам"` знаходить t1 по назві, `q="OOM"` — по опису; `q="%"` не повертає все.
- AC-6: Каскадне видалення: після delete t1 підзадач і нотаток t1 у БД немає.
- AC-7: `setFocus` атомарний: `[t2,t7,t1]` → ранги 1,2,3; потім `[t9]` → t9=1, решта `null`.
- AC-8: `findStale({ minDays: 3, now })` на seed → t1, t3, t12 (не t9 — свіжа, не t2 — todo).
- AC-9: Після seed `getHeat` по 12 задачах дає всі 7 рівнів; двічі seed → 12 задач (TC-19).
- AC-10: createRun → appendStep×3 → finishRun → кроки в порядку `index`, у run є `finishedAt`.

## Рішення (технічні, без зміни поведінки)
1. **`dueAt`: `null`, а не `undefined`.** У БД і `TaskSchema` поле `dueAt: string | null`. `HeatInput.dueAt` розширюємо до `Timestamp | null`, у `getHeat` перевірка стає `task.dueAt != null`. У `getHeat.test.ts` додаємо кейс `dueAt: null` → не alarm.
2. **Типи UI виводимо з `TaskSchema`.** `HeatInput = Pick<Task, "status" | "priority" | "updatedAt" | "dueAt">`, `TaskRowData = Pick<Task, "id" | "title" | "description" | "status" | "priority" | "createdAt" | "updatedAt" | "dueAt">`. Тимчасові ручні типи і коментарі «з'явиться в DEV-003» прибираємо. Оновлюємо `TaskRow`, `HeatBadge`, `sampleTasks` (додати `dueAt: null`) і `UiKitView`, якщо там є залежність від типу. Параметр `now` лишається `Timestamp`.
3. **Note — частина агрегату Task.** `NoteSchema` і `NoteCreateInputSchema` кладемо в `entities/task/model/schemas.ts`, а **не** в `entities/note`, як пише спека §4. Причини:
   - `TaskSchema` містить `notes[]`;
   - boundaries забороняють імпорт між сусідніми slices `entities/*`;
   - нотатка не існує без задачі (каскадне видалення).

   Поведінка не змінюється, це лише розміщення файлів. Відхилення фіксуємо в `docs/vault/decisions.md`. Slice `entities/note` не створюємо, поки немає UI нотаток. `SubtaskSchema`, `SubtaskCreateInputSchema` — у тому ж файлі (так і в спеці).
4. **Схеми `entities/task`** (типи лише через `z.infer`, експорт через `entities/task/index.ts`):
   - `TaskSchema`: `id`, `title`, `description`, `status`, `priority`, `createdAt`/`updatedAt` (ISO), `dueAt` (ISO | null), `focusRank` (int ≥ 1 | null), `subtasks: SubtaskSchema[]`, `notes: NoteSchema[]`;
   - `TaskListItemSchema` = `TaskSchema.omit({ subtasks, notes })` + `subtaskCount`, `subtaskDone` (контракт DEV-004: `listTasks` віддає агрегати одним SQL без N+1, DEV-004 не переписуватиме repository);
   - `SubtaskStatusSchema` (= статуси задачі), `SubtaskSourceSchema` (`user|ai`), `SubtaskSchema`, `NoteSchema`.
5. **Create/Update-схеми і defaults Zod 4.** У Zod 4 `.partial()` на полях з `.default()` все одно підставляє default. Тому:
   - базові поля оголошуємо без defaults (`TaskTitleSchema` = trim 3–120, `TaskDescriptionSchema` = trim 5–2000, `dueAt` = `z.iso.datetime({ offset: true })`);
   - `TaskCreateInputSchema` додає `.default("todo")` / `.default("medium")`;
   - `TaskUpdateInputSchema = z.object({ title, description, status, priority, dueAt: … .nullable() }).partial().strict()` + `refine` «хоча б одне поле».

   `id`, `createdAt`, `updatedAt`, `focusRank` в update заборонені (strict). Фокус змінюється лише через `setFocus`. Тест: `parse({ title })` не містить `status`.
   - `SubtaskCreateInputSchema`: `title` trim 1–200, `source`, `estimate?`, `rationale?`.
   - `SubtaskUpdateInputSchema`: `status` і/або `title`, strict, ≥ 1 поле.
   - `NoteCreateInputSchema`: `text` trim 1–2000.
6. **Список: `TaskListQuerySchema` в entities.** Поля: `status?`, `q?` (trim, порожній → без фільтра), `sort: "priority" | "createdAt"` (default `priority`), `order: "asc" | "desc"` (default `desc`). DEV-004 перевикористає схему для query.
   - SQL для `priority`: `CASE priority WHEN 'high' THEN 3 WHEN 'medium' THEN 2 ELSE 1 END {order}, createdAt DESC, id ASC`. Тай-брейк «новіші вище» однаковий для asc і desc (TC-11).
   - Для `createdAt`: `createdAt {order}, id ASC`.
   - `id` — стабільний тай-брейк для детермінованих тестів.
7. **Пошук нечутливий до регістру і для кирилиці.** Вбудований `LIKE` у SQLite ігнорує регістр лише для ASCII. Тому в `createDb` реєструємо детерміновану UDF `db.function("unicode_lower", { deterministic: true }, s => s.toLowerCase())`. Умова пошуку: `unicode_lower(title || ' ' || description) LIKE ? ESCAPE '\'`, параметр — `%${escapeLike(q.toLowerCase())}%`, де `escapeLike` екранує `\`, `%`, `_`. Окрему нормалізовану колонку не беремо: не треба синхронізувати її при кожному update, а для 12–100 задач повний скан не має значення. Тести: `q="пам"` і `q="ПАМ"` → t1, `q="OOM"` → t1, `q="%"` і `q="_"` → порожньо.
8. **`updatedAt` — доменне правило в service, атомарність у repository.**
   - `service.updateTask` читає поточну задачу і вмикає `touch`, лише якщо `title`/`description`/`status`/`priority` **фактично змінилися**. Збереження форми з тими самими значеннями або зміна лише `dueAt` не «охолоджує» задачу: `dueAt` за спекою не оновлює `updatedAt`.
   - Repository приймає `{ now, touch }` і оновлює `tasks.updatedAt` у тій самій `db.transaction` (`better-sqlite3` синхронний, тож між читанням і записом нічого не вклинюється).
   - `addSubtasks` / `updateSubtask` / `deleteSubtask` / `addNote` завжди оновлюють `updatedAt = now` батьківської задачі в одній транзакції.
   - `setFocus` `updatedAt` не чіпає. `createdAt` пишеться лише в `createTask`.
   - Clock: `createTaskService({ db, clock = () => new Date() })`. Усі дати пишемо як `toISOString()` (UTC, однаковий формат), тому порівняння рядків у SQL коректне. `dueAt` з офсетом нормалізуємо до UTC.
9. **`findStale({ minDays, now })`:** `status = 'in-progress' AND updatedAt <= now − minDays·DAY` (ISO-рядок). Це те саме, що `daysBetween(updatedAt, now) >= minDays` з `getHeat` (floor діб). Сортування — `updatedAt ASC`.
10. **Трасування агентів.**
    - У `entities/agentRun/model/schemas.ts` **додаємо** `AgentRunKindSchema`, `AgentRunStatusSchema`, `AgentRunModeSchema` (`live|demo`), `AgentStepTypeSchema`, `AgentStepRecordStateSchema` (`done|fail`), `AgentRunSchema`, `AgentStepRecordSchema`.
    - Наявні UI-схеми `AgentStepStateSchema` / `AgentStepSchema` (`pending|run|…`) не змінюємо.
    - `resultJson` / `errorJson` / `payloadJson` — текстові JSON-колонки. Repository серіалізує `unknown` на запис і повертає `unknown` на читання; валідація конкретних результатів — у DEV-008.
    - `appendStep` присвоює `index = COUNT(кроків run)` у транзакції, тож викликач не веде лічильник.
    - Payload не логуємо.
11. **Drizzle-схема і цілісність.**
    - Enum-колонки — `text({ enum: XSchema.options })` + `check(... IN (...))`. У SQLite drizzle-enum працює лише на рівні TS, CHECK — захист на випадок, якщо запис обійде Zod.
    - Індекси — зі спеки. FK `on delete cascade` (subtasks, notes, agent_steps). `agent_runs.taskId` — FK `on delete set null`: історія агента не має ламати видалення задачі.
    - Колонку `index` в `agent_steps` іменуємо `"index"`; drizzle лапкує її сам.
12. **Міграції.** `drizzle.config.ts` у корені (`dialect: "sqlite"`, `schema: ./src/server/db/schema.ts`, `out: ./src/server/db/migrations`). SQL і `meta/` комітимо. Скрипт `db:generate` = `drizzle-kit generate`. `migrate()` з `drizzle-orm/better-sqlite3/migrator` бере `path.join(process.cwd(), "src/server/db/migrations")` (`next dev`/`start`, Vitest і `db:seed` запускаються з кореня).
13. **З'єднання.**
    - `createDb(url)` — фабрика:
      - парсить `:memory:` / `file:<path>` / звичайний шлях;
      - для файлу: шлях від `process.cwd()`, `mkdirSync(dirname, { recursive: true })`;
      - `PRAGMA foreign_keys = ON`, `journal_mode = WAL` (лише для файлу), реєструє UDF, запускає `migrate()`;
      - повертає `{ db (drizzle), sqlite, close }`.
    - `getDb()` — синглтон з `env.DATABASE_URL` у `globalThis` через `declare global { var __devlogDb: … | undefined }`, без `as`. Якщо ESLint `no-var` спрацює в `declare global` — точковий `eslint-disable-next-line` з поясненням.
    - Тести використовують лише `createDb(":memory:")` або файл у `os.tmpdir()`.
14. **Seed.**
    - `seedDatabase(db, now)` у `src/server/db/seed.ts`. У транзакції:
      - `DELETE FROM agent_runs` (кроки — каскадом) і `DELETE FROM tasks` (підзадачі й нотатки — каскадом);
      - вставка t1…t12 з фіксованими `id`.
    - Дати: `ago(d) = now − d·DAY`, `dueAt` t2 = `now + 20 год`, решта `null`; `focusRank` = `null`.
    - Підзадачі: `source: "user"`, `position` = індекс у масиві, `createdAt` = `createdAt` задачі (для `done` — `updatedAt` задачі). Прототип дат підзадач не має.
    - `id` підзадач і нотаток — `nanoid()`. Ідемпотентність = ті самі 12 задач з тими самими `id` задач.
    - CLI `src/server/db/seedCli.ts`: `seedDatabase(getDb().db, new Date())` + `logger.info({ tasks: 12 })`.
    - `npm run db:seed` = `tsx --conditions=react-server src/server/db/seedCli.ts`. **Нова dev-залежність `tsx`:** запускає TS з aliases `@/` без збірки; умова `react-server` резолвить `server-only` у порожній модуль, без неї CLI падає на імпорті `env.ts`.
    - `npm run dev` сам seed не запускає (порожній стан теж валідний, спека п. 8).
15. **Залежності** (пояснення в PR):
    - `better-sqlite3`, `drizzle-orm` (runtime); `drizzle-kit`, `@types/better-sqlite3`, `tsx` (dev) — SQLite лежить у файлі, інфраструктура не потрібна, `npm run dev` працює без Docker;
    - `nanoid` — за спекою, короткі URL-safe id для `/tasks/:id` (альтернатива без залежності — `crypto.randomUUID()`; якщо рев'ю вирішить інакше, міняємо в одному місці `server/tasks/ids.ts`).
16. **Next і нативний модуль.** `better-sqlite3` уже є в дефолтному списку `serverExternalPackages` Next. Розробник перевіряє `node_modules/next/dist/lib/server-external-packages.json*`. `next.config.ts` міняємо, лише якщо пакета там немає.
17. **Node.**
    - Розробник виконує `node -v` і `npm ci` на чистому `node_modules`. Перевіряє, що `better-sqlite3` встановився з prebuilt (без компіляції `node-gyp` у виводі) і `npm test` зелений.
    - Після цього звужує `engines.node` до перевіреного LTS-діапазону (`>=22 <N`, де N — перша мажорна версія без prebuilt) і додає `.nvmrc` з мажорною версією, на якій перевіряли.
    - Фактичну версію записує в PR.
18. **Межі.** `server/**` імпортує контракти лише з `@/entities/task` і `@/entities/agentRun` (index). Route handlers і агенти SQL не пишуть, бо DB-клієнт доступний тільки через repository/service. Якщо drizzle-kit не завантажить `schema.ts` через імпорт з `@/entities/task` (alias або UI-код в index):
    - fallback — локальні масиви literal-ів у `schema.ts`;
    - плюс unit-тест рівності з `XSchema.options`, щоб списки не розійшлися.

## Ризики
- **Нативний `better-sqlite3`:** якщо під поточний Node немає prebuilt, `npm install` компілює через `node-gyp` (потрібні Xcode CLT або build-essential). Пом'якшення — рішення 17: `engines` + `.nvmrc` на перевірений LTS. Якщо перевірка провалиться, зупиняємось і повідомляємо.
- **drizzle-kit і aliases / UI в `entities/task/index.ts`:** завантаження схеми може впасти. Fallback — рішення 18.
- **Розходження схеми і міграцій:** після правки `schema.ts` треба перегенерувати міграції. У DoD — `npm run db:generate` не створює нового файлу.
- **`process.cwd()` для міграцій:** запуск не з кореня (наприклад, standalone-збірка) не знайде теку. Зараз усі сценарії стартують з кореня; standalone не використовуємо.
- **HMR і кілька з'єднань:** синглтон на `globalThis`. WAL дозволяє паралельне читання; `db:seed` під час `npm run dev` безпечний, бо SQLite блокує запис.
- **UDF `unicode_lower` існує лише в нашому з'єднанні:** зовнішні інструменти (drizzle-studio, `sqlite3` CLI) не виконають запит пошуку. Це прийнятно, функцію використовує лише repository.
- **Зміна типів DEV-002:** `dueAt: null` і `Pick` від `Task` зачіпають UI-компоненти. Регресію ловлять typecheck і наявні тести.
- **Обсяг:** перевірка й рев'ю (opus + Codex + security) будуть довгими, бо це найбільша серверна задача на цей момент.
- **Eng-review:** gstack `/plan-eng-review` інтерактивний і в режимі subagent не запускався. Якщо потрібен, orchestrator може провести його до `APPROVE`.
