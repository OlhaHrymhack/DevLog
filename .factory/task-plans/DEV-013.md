# DEV-013 — README і перевірка з нуля

## Мета

Здати проєкт: README, з яким перевіряльник запускає застосунок за 2 хвилини і розуміє архітектуру й чотирьох агентів; підтвердження, що clean clone працює; повний прогін перевірок. Закриває R-11, R-12, R-13, R-16, R-09; TC-60…65. Специфікація — `docs/vault/specs/DEV-013.md`.

Рішення користувачки 2026-11-23: README.md ще не існує — створюю його сама з усіма розділами спеки, а розділ «Рішення і компроміси» лишаю лише заголовком із рядком «пише авторка» (текст розділу пише вона вручну; hook забороняє мені його редагувати).

## Контекст

- Агенти A–D змерджені в `stage` (DEV-009…012, PR #25, #27, #28, #29). Факти про кроки, tools, схеми, валідацію й хибні кейси беру з коду (`src/server/agents/*`, `src/entities/agentRun/model/*`), специфікацій `docs/vault/specs/DEV-009…012.md` і `docs/vault/decisions.md`, а не з пам'яті.
- Змінні середовища — з `.env.example` (таблиця в README має збігатися з файлом).
- Продукт і матриця R-xx — `docs/vault/product.md` §4.

## Зачеплені файли

- `README.md` (новий): 12 розділів зі спеки; «Рішення і компроміси» — лише заголовок.
- `docs/vault/product.md` §4 — статус покриття R-xx («зроблено» / «пояснено в README»).
- Код застосунку не змінюється.

## Рішення

1. Структура README — рівно за розділами 1–12 зі спеки; кожен агент описаний за 7 пунктами (навіщо, кроки й tools, як вирішує що далі, коли зупиняється, structured output, валідація, підтвердження користувачем).
2. Хибні кейси (3): A — посилання на задачу #42; B — дублікати наявних підзадач; C — згадка PR #999. Для кожного: що повернула модель → що зловила перевірка → що бачить користувач; відтворення через dev-панель «Зламати відповідь агента» (працює при SPA-навігації зі списку).
3. Live і mock: чесно зазначити, що на реальному API перевірено лише smoke-агента (`npm run smoke:ai`), а схеми `DayPlan`/`Decomposition`/`StatusUpdate`/`Triage` на live OpenAI не перевірені; demo — той самий цикл `runAgent` з `ScriptedClient`.
4. Відомі відхилення від спеки (немає `detail` у кроках агентів, DEV-012 tier balanced без Codex) — окремим коротким блоком у «Що свідомо не робимо / відомі обмеження».
5. Перевірка з нуля — у тимчасовій теці `git clone` гілки без `.env` і `data/`; плану платних запитів немає. Ручні кроки сценаріїв (A→фокус, B→clarify→створити, C→копіювати, D→чернетка, зламана відповідь) покриті наявними E2E; у evidence — виводи команд.
6. Пошук ключа-маркера в `.next/static` після `npm run build` — з порожнім ключем (нічого секретного не читаємо й не виводимо).

## Acceptance criteria (зі специфікації, нумерація збережена)

- **AC-1** Clean clone запускається командою з ТЗ (`npm install && npm run dev`, demo-режим). [M]
- **AC-2** `npm run lint && npm run typecheck && npm test && npm run test:e2e` зелені. [M]
- **AC-3** `.env.example` повний і порожній; таблиця в README збігається з файлом. [U] тест DEV-001 зелений; [M] звірка.
- **AC-4** README описує кожного агента за 7 пунктами. [M]
- **AC-5** README описує ≥ 2 (беремо 3) хибні кейси з відтворенням. [M]
- **AC-6** Межі авторства: diff README не зачіпає текст розділу «Рішення і компроміси», `AGENT_LOG.md` не змінено. [M]
- **AC-7** Матриця ТЗ закрита: кожна R-xx у `product.md` §4 позначена «зроблено» або «пояснено в README». [M]

## Як перевірити

`factory verify DEV-013 --full` (typecheck, lint, unit, E2E) + ручна перевірка clean clone у `/tmp`-теці з логом у evidence. Для AC без автотестів (документація) — ручні чекліст і диф; автотест, який перевіряє, що README містить обов'язкові заголовки й що таблиця змінних збігається з `.env.example`, додам у `test/` (щоб AC-3/4 були не лише ручними).
