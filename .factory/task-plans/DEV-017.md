# DEV-017 — підготовка DevLog до здачі

Специфікація та критерії приймання — [DEV-017](../../docs/vault/specs/DEV-017.md). Окремих змін до макета немає. Для відмови агента використовуємо наявний UI помилок.

## Реалізація

- Документація й контейнер. Оновити README та `.env.example`. Додати багатостадійний Dockerfile, Compose з іменованим томом для SQLite і `.dockerignore`. За замовчуванням публікувати порт контейнера лише на localhost. Використати версію Node проєкту та документований Next.js standalone для контейнера з потрібними міграціями та статиками. За потреби додати .vercelignore для захисту завантаження з CLI.
- README, розділ «Як ми розробляли DevLog». Одним коротким блоком описати Discovery, план із критеріями та оцінку ризику (fast / balanced / strong), погодження плану для balanced/strong, реалізацію з тестами, `verify`, незалежне рев’ю (security і друге рев’ю за ризиком), E2E і QA за потреби, фінальне погодження, PR у `stage` та merge авторкою, документацію і ретро. Пояснити цикл виправлень: знахідка повертає задачу до реалізації, зміни знову проходять перевірки та рев’ю для нового хеша. Описати дію CLI, git hooks і CI, а також межі механізму: покриття тестів і якість AI-рев’ю залежать від сценаріїв і звітів, фінальне рішення приймає людина. Навести перевірений приклад із DEV-013 (один невдалий verify, одне блокувальне рев’ю та цикл виправлень) і за потреби результат selftest базового `stage` (162 пройшли, 0 провалів, перевірено під час планування), з посиланням на докази. Перевірити актуальність захисту гілок перед будь-яким твердженням про примусові перевірки на GitHub.
- README, розділ про рішення MVP. Пояснити простими словами: ТЗ не вимагало реєстрації та входу до акаунта (автентифікації), ролей і прав доступу (авторизації). Через обмежений час їх і багатокористувацький режим відклали. Ролі визначали б, наприклад, хто може лише переглядати задачі, а хто — створювати, редагувати й видаляти їх. Початковий MVP залишив SQLite локально через час і простий старт із чистого клону; локальний запуск і Docker використовують SQLite, а публічний Vercel — окрему демобазу. Описати наслідок для демо: усі відвідувачі працюють зі спільними синтетичними задачами. Прибрати застарілу згадку про відсутність деплою після появи перевіреної адреси.
- Дані. Використати Turso/libSQL на Vercel і локальний SQLite-файл через сумісний клієнт. Перевести репозиторії, інструменти агентів, CLI та ініціалізацію на асинхронний контракт із тим самим SQLite-схематом. Явно перевірити сумісність історії міграцій, відкриття старого файла, каскади та атомарні записи. Поточний Unicode-пошук покладається на локальну функцію SQLite. Зберегти результат пошуку й серверну пагінацію через нормалізований текст і міграцію наявних записів, із перевіркою буквальних wildcard-символів. Для віддаленої бази виконувати міграції та одноразове засівання синтетичними задачами окремо від старту функцій. Перевірити, що всі операції в транзакціях використовують саме транзакційне з’єднання, зокрема focus, позиції підзадач і нумерація кроків. Захистити звичайний локальний seed від випадкової роботи з production.
- Квота. Додати SQLite-таблицю зі стабільним ключем типу агента. Сервер виконує один умовний атомарний запис, який резервує спробу лише за лічильника менше 10. Підключити в спільному обробнику після валідації запиту і до створення клієнта моделі або стріму. У Vercel Production квота обов’язкова з постійною базою та без скидання під час deploy або seed. HTTP 429 після вичерпання й 503 при помилці сховища. Перевірити маршрути, які з’являться до релізу, зокрема DEV-016, якщо його змерджать.
- Реліз. Узгоджені налаштування зберігати у Vercel Environment Variables. Production має власну демобазу й виділений серверний ключ OpenAI. Зафіксувати та перевірити обмеження кроків і токенів для цього деплою. Квота рахує запуски агента, а один запуск може містити кілька викликів моделі. Preview працює без платного ключа, зі своїми даними. Режим live зі спільною квотою відкривати лише після перевірки захисту. Для посилання використати production-домен після merge в узгоджену гілку. Реальні облікові дані й публічний запуск потрібні на етапі релізу.
- Гігієна. Перший огляд Git не знайшов закомічених скріншотів. `.next`, `test-results`, локальна БД та env ігноруються Git. Перевірити Docker/Vercel build context і залишити потрібні дизайн-референси та записи Factory.

## Перевірки

- AC-1/2. Звірити опис Factory з правилами, CLI, hooks, CI і доказами. Перевірити команди з чистого клону та Docker з новим томом, health, CRUD і збереження після повторного створення контейнера.
- AC-3. Прогнати наявні регресійні тести та додати тести міграцій для старого SQLite-файла й окремої віддаленої бази. Перевірити Unicode, каскади, транзакції та NDJSON.
- AC-4/5. Запустити інтеграційні тести з понад 10 паралельними запитами через незалежні з’єднання, з перевіркою 10/11, незалежності агентів, збереження після реконекту і помилки сховища. Підмінений клієнт моделі підтверджує нуль викликів для відхилених запитів. Додати браузерний сценарій для повідомлення про вичерпану квоту.
- AC-6/7. Перевірити склад контексту збірки, demo Preview, production health, читання задач і CRUD на публічному URL. Обмеження 10/11 перевірити до відкриття платного production, без витрат із публічного пулу.
- `factory verify DEV-017 --full`, незалежні review, security, Codex і QA. Реліз після фінального погодження й merge. Не зараховувати ручні перевірки, доки вони не виконані.
