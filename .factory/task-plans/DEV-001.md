# DEV-001 — Каркас і tooling

## Мета
Порожній, але повністю робочий застосунок: `npm install && npm run dev` стартує без `.env`, усі команди (`typecheck`, `lint`, `test`, `test:e2e`) зелені, межі архітектури (FSD + `server`) перевіряються ESLint-ом, серверний env валідується Zod-ом на старті. Після задачі будь-яку фічу можна додавати без налаштувань tooling.

## Контекст
- Джерело правди: `docs/vault/specs/DEV-001.md` (AC-1…AC-7 перенесено без зміни нумерації), наскрізні домовленості — `docs/vault/specs/README.md`, стайл-гайд — `.claude/rules/code-style.md` (D-013, D-014), тести — `.claude/rules/testing.md`.
- Коду застосунку немає: ні `package.json`, ні `tsconfig.json`, ні `src/`. Вже є й **не перезаписуються**: `.factory/`, `.claude/`, `docs/`, `.githooks/`, `.github/`, `.gitignore`.
- `.gitignore` вже ігнорує `.env*` (крім `!.env.example`), `node_modules`, `.next`, `coverage`, `test-results`, `playwright-report`, `data/*.db*`, `.claude/prompt-log.md`, `.claude/settings.local.json` — рядки з `create-next-app` лише **дописуються**, якщо їх бракує (напр. `next-env.d.ts`, `*.tsbuildinfo`).
- `.githooks/pre-commit|pre-push` викликають `node .factory/bin/factory.mjs gates` — не змінюються (DoD специфікації, D-004).
- CI (`.github/workflows/ci.yml`): Node 22, `npm ci` → потрібен закомічений `package-lock.json`; `typecheck && lint && test`; потім `npx playwright install --with-deps chromium && npm run test:e2e` з `AI_MODE: demo`. Уже оновлено з `AI_MOCK` на `AI_MODE` — не чіпаємо.
- `factory verify` = typecheck + lint + test; `verify --full` додає `npm run test:e2e` — для AC-2 потрібен саме `--full`. Tree hash — з git-індексу (D-002): файли, які `next dev`/`next build` переписує (`next-env.d.ts`, `tsconfig.json`), мають бути стабілізовані й закомічені до verify.
- Traceability gate (`.factory/bin/core.mjs`) шукає кожен `AC-n` з цього плану в тестових файлах (`**/*.test.ts(x)`, `**/*.spec.ts`, `e2e/**`) → у плані згадуються лише AC-1…AC-7, і кожен має тест із назвою `DEV-001 AC-n: …`.
- Рішення користувачки (зафіксовано): змінна режиму — `AI_MODE=live|demo`; без значення — `live` при наявному `ANTHROPIC_API_KEY`, інакше `demo`. Env валідується eagerly при старті сервера через `src/instrumentation.ts`.
- Середовище: Node 22.22.3, npm 10.9.8; актуальні next 16.x (без `next lint` → `lint` = `eslint .`), eslint 10.x (flat config), eslint-plugin-boundaries 7.x.

## Acceptance criteria
- AC-1: Clean clone → `npm install && npm run dev` без `.env` стартує; `GET /` віддає 200; `GET /api/health` → `{ "status": "ok", "aiMode": "demo" }`.
- AC-2: `npm run typecheck`, `npm run lint`, `npm test`, `npm run test:e2e` зелені на чистому каркасі (evidence — `factory verify DEV-001 --full`). Уточнення: сюди ж віднесено перевірку, що `package.json` містить усі скрипти з п.7 специфікації, `prepare` не падає поза git-репозиторієм, а `*.test.tsx` виконуються в `jsdom` (інакше конфіг середовищ Vitest ніщо не перевіряє).
- AC-3: `aiMode` визначається правильно: без ключа → `demo`; з ключем → `live`; `AI_MODE=demo` з ключем → `demo`; `AI_MODE=foo` → помилка. Уточнення: порожній рядок (`ANTHROPIC_API_KEY=` як у скопійованому `.env.example`) трактується як відсутнє значення → `demo` (інакше порожній ключ дав би `live`).
- AC-4: Невалідний env дає зрозумілу помилку з назвою змінної і без значень: `LOG_LEVEL=loud` → повідомлення містить `LOG_LEVEL`; текст помилки не містить ні значення ключа, ні самого невалідного значення (`loud`).
- AC-5: Ключ не потрапляє в клієнт і логи: logger з `redact` — лог об'єкта з `apiKey` (на верхньому рівні й вкладеного), `headers.authorization`, `ANTHROPIC_API_KEY` → `[Redacted]`; [M] `ANTHROPIC_API_KEY=<маркер> npm run build` + пошук маркера в `.next/static` → 0 збігів (маркер передається лише через env команди, не через `.env`).
- AC-6: ESLint ловить порушення стайл-гайду (прогін ESLint API з конфігом проєкту на фікстурах поза `src/`): `const X = () => …` компонент → error (`func-style`); `export default` у `features/` → error; імпорт `widgets` з `entities` → error; імпорт `src/server` з `features` → error; `console.log` → error. Уточнення (додаткові кейси того ж AC, без зміни суті): сусідній slice того ж шару → error; глибокий імпорт у slice повз `index.ts` → error; `any` → error; `as string` → error, `as const` → ok; «чиста» фікстура → 0 помилок (контроль, що фікстури реально лінтяться, а не ігноруються).
- AC-7: `.env.example` містить усі змінні Zod-схеми серверного env (рівно ті самі ключі), усі значення порожні, до кожної змінної — коментар.

**Задачі:** немає. Розблоковує всі.

## Ризики
- **Сумісність eslint 10 / `eslint-config-next` 16 / boundaries 7** — peer-конфлікти або зміна API правил (`element-types` → `dependencies`, синтаксис шаблонів). Мітигація: AC-6 перевіряє конкретні `ruleId`; fallback (`eslint-plugin-import`) і pin версії — з записом у decisions.
- **`eslint .` лінтить фабрику** (`.factory/bin/*.mjs`, `.claude/hooks/*.mjs` з `console`/default export) → lint червоний. Мітигація: `ignores` у кроці 10.
- **Фікстури AC-6 «тихо» ігноруються** (ignore-патерни, невідповідність `basePath`) → тест зелений без перевірки. Мітигація: контрольна чиста фікстура + `isPathIgnored` + перевірка `ruleId`.
- **Boundaries не резолвить імпорт** → мовчки пропускає (unknown element). Мітигація: резолвер typescript, реальні файли у фікстурах, за потреби `boundaries/no-unknown`.
- **`next dev`/`next build` переписують `tsconfig.json`/`next-env.d.ts`** → evidence застаріває після e2e. Мітигація: крок 14 — стабілізувати й закомітити до verify.
- **`server-only` у Vitest** кидає помилку. Мітигація: alias на стаб тільки в `vitest.config.ts`; у Next-збірці захист лишається.
- **pino-pretty у Next** (worker transport, бандлинг) → падіння dev-сервера. Мітигація: `serverExternalPackages`, transport лише в development; при проблемах — `pino-pretty` як stream замість transport.
- **Помилка env у dev** може лише залогуватися, а не зупинити `next dev`. Прийнятно: `/api/health` тоді віддає 500 через той самий `getServerEnv()`; поведінку фіксує QA.
- **`func-style: declaration`** забороняє будь-які `const f = () => …` у `src/` (не лише компоненти) — суворіше, ніж «компоненти», але відповідає специфікації; inline-колбеки не зачіпаються.
- **Дефолтна розмітка/стилі `create-next-app` і shadcn CSS-змінні** у `globals.css` — тимчасові, замінюються в DEV-002.

## Відкриті питання
- `AI_MODE=live` без `ANTHROPIC_API_KEY`: специфікація каже лише «примусово». Пропозиція — помилка валідації env на старті з назвами `AI_MODE`/`ANTHROPIC_API_KEY` (без значень), щоб не падати пізніше на першому виклику агента. Без відповіді — реалізуємо буквально (примусовий `live`, помилка з'явиться в DEV-008) і тест на це не пишемо.
- `codeGlobs` у `.factory/project.config.json` не охоплюють `eslint.config.*`, `postcss.config.*`, `components.json`, `.env.example`, `eslint-fixtures/**`, `test/**` — hook не блокуватиме їх редагування поза IMPLEMENTING (на tree hash це не впливає). Чи розширити список? Це зміна фабрики — окремим PR `factory/…` лише з вашого погодження; у DEV-001 не змінюємо.
