# DevLog — продукт, скоуп MVP і тест-кейси

> **Джерело правди про продукт.** Описує, що будуємо і навіщо, що входить у MVP і за якими тест-кейсами фіча вважається готовою.
> Ієрархія джерел: **ТЗ** (PDF замовника, поза репо) → **цей документ** → **[[specs/README|специфікації задач]]** (`docs/vault/specs/DEV-xxx.md`: реалізація, контракти, мікрокопі, AC з тест-кейсами, порядок виконання) → `docs/design/DESIGN.md` + `prototype.html` (як це виглядає і поводиться) → `.factory/task-plans/<ID>.md` (план architect-а).
> Тест-кейси нижче — рівень ТЗ; детальні AC з тестами — у специфікаціях, з посиланнями на TC-xx.
> Якщо нижчі за ієрархією джерела суперечать вищим — виграє вище, а розбіжність фіксується в [[decisions]].
> Розділ README «Рішення і компроміси» і `AGENT_LOG.md` пише авторка — тут лише вимоги до них.

## 1. Проблема і користувач
- **Хто:** невелика інженерна команда, один спільний трекер. Без авторизації: один користувач, одна команда.
- **Біль (з ТЗ):** люди вручну розбираються, що робити далі, пишуть підзадачі й складають апдейти для колег. Це займає час і дратує.
- **Що робимо:** простий трекер задач і AI-шар поверх нього, який прибирає цей friction.

## 2. Концепт
DevLog — трекер, де AI **пропонує**, а людина **вирішує**. Чотири агенти закривають чотири моменти дня:

| Момент | Агент | Що дає людині |
|---|---|---|
| Ранок: «з чого почати?» | **A. План на день** | top-3 задачі з поясненням, чому саме вони, і що свідомо відкладено |
| Задача незрозуміла / велика | **B. Декомпозиція** | 3–6 підзадач з оцінкою; якщо задача розмита — спершу уточнююче питання |
| Треба відзвітувати | **C. Статус-апдейт** | короткий Slack-апдейт у тоні під контекст, лише з підтвердженими фактами |
| Задачі тихо застрягли | **D. Радар застряглих** (власна ідея) | знаходить in-progress задачі без руху, називає ймовірну причину і пропонує конкретну дію |

**Навіщо D:** застряглі задачі — найдорожчі для команди, бо їх ніхто не помічає, доки не стало пізно. A каже, що робити сьогодні, але не каже, *чому* щось стоїть тиждень. D дивиться на історію (дні без змін, нотатки, підзадачі), ставить діагноз (чекає ревʼю / розмита / завелика) і пропонує дію: чернетку запиту на ревʼю, декомпозицію через B або прохання про допомогу.

**Принципи** (деталі — `DESIGN.md` §1):
1. AI пропонує, людина вирішує: жоден агент не змінює дані без кнопки підтвердження.
2. Агент показує, що думає: кроки зі станами, прогрес, «Зупинити».
3. Output агента не довіряємо: Zod-схема + перевірка фактів → 1 повтор → детермінований fallback.
4. Працює без ключа: demo-режим з детермінованими моками, з ключем — реальний API.
5. Гумор лише в мікрокопі; ніколи — в помилках, видаленні й апдейтах для менеджера. Серйозний варіант текстів є, але в production перемикача немає (D-015).

## 3. Скоуп MVP
**Обов'язково (ТЗ):** CRUD задач; список з фільтром за статусом і сортуванням за пріоритетом/датою; зберігання між перезавантаженнями; ≥ 2 агентні AI-функції (беремо всі 4); `.env.example`; запуск `npm install && npm run dev`; README з дизайном агентів; `AGENT_LOG.md`.

**Понад ТЗ (D-014), бо підсилюють агентів:** підзадачі й нотатки (вхід для B, C, D); `dueAt` і `updatedAt` (вхід для A і D); «температура» задачі; пошук; `focusRank` («Фокус #N») від A; demo-режим і fault injection для показу fallback.

**Можна вирізати при нестачі часу (у такому порядку):** гарячі клавіші, «Серйозний режим», dev-панель → друк посимвольно в C → агент D повністю. Вирізане — пояснюється в README (ТЗ: «краще прибрати одну фічу і пояснити чому»).

**Свідомо не робимо:** авторизацію, кількох користувачів і assignees, drag-and-drop, реальну відправку в Slack, деплой, ручне додавання підзадач (лише через агента B), перемикач «Серйозного режиму» в production (лише dev-панель) — D-015.
