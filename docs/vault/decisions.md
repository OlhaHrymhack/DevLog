## D-016 Полегшена фабрика: ручна ескалація, тести до рев'ю, маршрути за tier
- Дата: 2026-11-22
- Supersedes: D-005 (частково: reviewer для fast — sonnet; QA пропускають також не-UI задачі), D-008 (уточнення: codex лише для strong за класифікацією, ескалація моделі його не вмикає).
- Рішення: (1) автоматичної ескалації після провалів verify/review немає: developer доробляє на поточній моделі, повтор помилки CLI розпізнає за відбитком, модель developer підвищує лише orchestrator (`factory escalate`); рівень рев'ю визначає tier (ризик зміни); 3 провали з developer на opus → BLOCKED. (2) Етап TESTING прибрано: developer пише тести на кожен AC в IMPLEMENTING, `verify` перевіряє AC traceability, рев'ю бачить код разом із тестами; QA лише запускає тести й перевіряє UI в браузері (balanced/strong з `ui=1`) і не править код чи тести. (3) Маршрути: fast — план пише orchestrator, developer haiku, reviewer sonnet; balanced — один прохід architect на sonnet, researcher лише за потреби; strong — researcher і architect на opus, security за ризиком, codex. (4) Orchestrator — Sonnet за замовчуванням; між етапами `factory line`, повний `report` — перед фінальним погодженням і при блокуванні. (5) Метрики на Task ID: `factory usage` / `factory metrics` — токени за ролями, цикли доопрацювання, час до PR.
- Причина: на DEV-001 два провали verify (`LayoutProps`, готовність Vitest — проблеми каркаса, не складності) автоматично підняли developer до Opus і ввімкнули обов'язковий codex; головна сесія на Opus дала найбільший обсяг повторного читання контексту. Погоджено користувачкою.
- Альтернативи: лишити авто-ескалацію з вищим порогом — відхилено, бо провал каркаса і складний дефект для CLI однакові.
- Ризик: ескалація тепер залежить від судження orchestrator; компенсація — ліміт BLOCKED і метрики. Ефект економії перевіряємо `factory metrics` на найближчих задачах.

## D-017 Реалізація balanced у головній сесії, рев'ю за ризиком, сумісність зі старими задачами
- Дата: 2026-11-22
- Доповнює: D-016.
- Рішення: (1) balanced реалізує головна сесія (Sonnet) без окремого developer; fast — developer haiku, strong — developer opus. (2) Модель рев'ю — за ризиком: sonnet для fast і balanced, opus для balanced із security/integrations ≥ 1 або criticality = 2 і для strong (`reviewModel.balancedElevated`). (3) Tier завжди рахується з балів classify (`effectiveTier`): підвищений старою фабрикою `task.tier` не визначає рівень рев'ю, QA і codex. (4) Відсутній `scores.ui` (стара задача) → QA обов'язковий; e2e потрібен і тоді, коли план вимагає `verify --full` / `test:e2e` (DEV-001 AC-2). (5) Повтор тієї самої діагностики verify/review не збільшує лічильник до BLOCKED; ліміт 3 лишається для різних спроб. (6) Після `APPROVE` orchestrator веде задачу без рутинних пауз до фінального погодження; `transition` оновлює наступну дію, `line` показує tier, модель реалізації й рев'ю («заплановано» / «підтверджено звітом»).
- Причина: швидше до PR і дешевше (немає другого Sonnet-developer поруч із Sonnet-оркестратором), видимість правок у терміналі; два дефекти з рев'ю PR #8 (повтори блокували задачу, стара ескалація DEV-001 вмикала б codex і вимикала б QA через відсутній `ui`). Погоджено користувачкою.
- Ризик: головна сесія і реалізує, і веде процес — незалежність забезпечує лише окремий reviewer у свіжому контексті; повтор помилки без ліміту можливий, але кожен повтор видно в `line` і `metrics`.

## D-018 Відновлення задач з gates, перевірки вчасно, Stop hook лише за зміни сесії
- Дата: 2026-11-22
- Доповнює: D-016, D-017.
- Рішення: (1) `factory resume <ID>`: tier і модель реалізації — з балів classify (стара автоескалація скасовується, ручні `escalate` лишаються); наступна дія виводиться зі статусу, approval і evidence для поточного хешу, збережений `nextAction` — лише нотатка; «продовжувати без питань», якщо approval чинний і план не змінився. (2) balanced із готовою специфікацією — план пише головна сесія (AC і посилання на прототип зі спеки); architect — коли спеки немає. (3) Тести — щойно є перший робочий сценарій; `verify` перед рев'ю; E2E перед фінальним погодженням, якщо його вимагає план або спека (`test:e2e`, Playwright, E2E), навіть без ручного QA. Зелений `verify` / `verify --full` для незмінного хешу перевикористовується; при падінні `verify` друкує лише команду й останні рядки діагностики. (4) Stop hook блокує, лише якщо код (`codeGlobs`) змінила саме ця сесія: база — відбиток на SessionStart у тимчасовій папці поза репо; compact її не скидає; сесія без бази не блокується.
- Причина: старий nextAction і автоескалація DEV-001 зупиняли або здорожчували відновлення; Stop hook вимагав `verify DEV-001` у кожному ході сесії, що змінювала лише фабрику. Погоджено користувачкою.
- Ризик: сесія, що почалась до оновлення hook-а, отримує базу на першому Stop — зміни коду до цього моменту їй не приписуються (компенсація: gates на transition і pre-commit не змінились).

## D-021 Рев'ю і security для одного зафіксованого хешу
- Дата: 2026-11-22
- Доповнює: D-016…D-019.
- Рішення: (1) вхід у REVIEWING фіксує хеш дерева (`reviewTree`); (2) усі обов'язкові рев'ю (reviewer, security, codex для strong) запускаються для цього хешу, код у цей час не змінюється; (3) `factory record review|codex|security` відхиляє звіт, якщо хеш змінився з початку рев'ю або задача не в REVIEWING; (4) повернення в IMPLEMENTING заблоковане, доки не прийшли всі обов'язкові звіти для зафіксованого хешу; (5) блокери (Critical/High) збираються з усіх звітів і виправляються одним пакетом, далі `verify` нового хешу і нове рев'ю; (6) selftest: зміна хешу між входом у рев'ю та записом звіту.
- Причина: на DEV-001 правки після першого звіту (security) зробили застарілими evidence решти рев'ю і змусили повторювати їх, а звіти приходили для різних станів коду. Погоджено користувачкою.
- Ризик: рев'ю доводиться чекати повністю навіть при очевидному блокері в першому звіті; компенсація — паралельний запуск, тож час майже не росте.
