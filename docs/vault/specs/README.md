# Специфікації задач DEV-001…013

> **Навіщо.** Кожна задача має повну специфікацію: що робимо, де в прототипі референс, які файли, контракти, мікрокопі, AC з тест-кейсами. Специфікація — **вхід** для `/factory <ID>`: researcher її читає, architect переносить AC у `.factory/task-plans/<ID>.md` **без зміни нумерації** і додає оцінку складності. Якщо architect змінює AC — фіксує це в плані з причиною.
> Ієрархія: ТЗ → [[product]] → **ці специфікації** → `DESIGN.md` / `prototype.html` → план задачі. Розбіжність — у [[decisions]].

## Як продовжити роботу після втрати контексту
1. `node .factory/bin/factory.mjs status` — яка задача поточна і в якому статусі.
2. Відкрити цей файл → наступна задача за порядком нижче, чиї залежності в статусі DONE.
3. Прочитати її специфікацію `specs/DEV-xxx.md` повністю, потім `now.md`.
4. `/factory DEV-xxx`. Нічого не вигадувати понад специфікацію; прогалина → питання користувачці.

## Наскрізні домовленості (діють у всіх задачах)
- **Доменна мова:** `Task`, `Subtask`, `Note`, `AgentRun`, `AgentStep`, `DayPlan` (A), `Decomposition` (B), `StatusUpdate` (C), `Triage` (D). Однаково в коді, API, БД, UI-типах.
- **Slices — camelCase** (D-014): `features/taskCreate`, `widgets/dayPlanPanel`, `entities/agentRun`. Карта компонентів — `DESIGN.md` §6 з цією поправкою.
- **Логіка агентів — лише на сервері** (`src/server/agents/<agent>/`). Клієнт — UI + хук, що читає NDJSON-стрім з `/api/agents/<agent>`.
- **Тексти** — `shared/config/copy.uk.ts`: кожен рядок з гумором має серйозну пару (`{ serious, funny }`). Точні тексти — з прототипу, вказані в специфікаціях.
- **Час:** усі дати в БД — ISO-рядки UTC; «днів без змін» = `floor((now − updatedAt) / 1 доба)`; `now` інжектується (параметр), щоб тести були детерміновані.
- **Помилки API:** `{ error: { code, message, details? } }`; коди: `VALIDATION_ERROR` 400, `NOT_FOUND` 404, `INTERNAL_ERROR` 500.
- **Назви тестів:** `"DEV-00X AC-n: <що перевіряє>"`; у специфікаціях тест-кейс позначено `[U]` unit, `[I]` integration, `[E]` E2E Playwright, `[M]` ручна перевірка.

## Рішення, прийняті в специфікаціях (перевірити користувачці)
1. **«Справжній агент» у live-режимі:** модель сама викликає read-tools (`list_active_tasks`, `get_task` …) і завершує `submit_*`. Детерміновані правила прототипу (`scoreTask`, `isVague`, `diagnose`, `autoTone`) — це (а) підказки, які tools повертають моделі, (б) логіка mock-клієнта, (в) fallback.
2. **Demo-режим = скриптований фейковий клієнт моделі**, що віддає ті самі `tool_use`-кроки. Тобто в demo працює той самий цикл `runAgent`, а не обхідний шлях.
3. **Fault injection** («Зламати відповідь агента») — лише `NODE_ENV !== 'production'`, передається полем `debug.forceInvalidOutput` у тілі запиту агента; у production поле відкидається схемою.
4. **«Ігнорувати» в D** — стан сесії на клієнті (`snoozedIds` передаються в запит), не в БД.
5. **Фокус дня** — поле `focusRank` у БД; нове застосування скидає попередні ранги.
